# v3.2 Unified Sync Audit (Phase 0)

Read-only inventory of every sync/load/derive/manual operation in the current codebase, done before designing the Unified Sync Engine. Produced by five parallel, independent code reads (not assumed from docs) covering Calendar/Staffline, Payslips/Annual Leave, Monzo/Finance/Savings, Dashboard/Action Centre/frontend loading, and cross-cutting infrastructure (locking, triggers, properties, existing sync-status tracking).

## How to read this

Classification:
- **A** — external source sync, safe/idempotent
- **B** — read-only application load
- **C** — derived calculation
- **D** — manual-review operation
- **E** — potentially destructive / requires confirmation

"Idempotent?" always cites the real dedup/upsert mechanism found in code, not assumed. "Unattended-safe?" is the verdict actually load-bearing for Phase 1-6 design.

## Architecture-critical findings (not in the matrix)

**1. A dormant, unused sync-history ledger already exists — reuse the pattern, but not the sheet.** `BANK_SYNC_HISTORY` (Finance/FinanceIntegrationConfig.js:145) is declared with almost exactly the schema this project needs (Sync ID, Started/Completed At, counts, Status), created by `setupPayTrackerFinanceIntegrations()` on every run, but **confirmed by grep that nothing has ever written a row to it**. Same for the `SYNC_STATUSES` enum (RUNNING/COMPLETE/COMPLETE_WITH_WARNINGS/ERROR) — declared, referenced nowhere else. Decision: introduce a new, honestly-named `Sync Status` sheet for the Unified Sync Engine (task-level, not Finance-specific — Calendar/Staffline/Payslips/Annual Leave aren't "bank" concepts) rather than repurposing a Finance-named sheet for cross-cutting state. `BANK_SYNC_HISTORY`/`SYNC_STATUSES` are left exactly as-is (never delete/rename an existing sheet) — noted here so nobody rediscovers this as "missing" work later.

**2. Only one locking idiom exists in the whole codebase: `PayTrackerUtils.withDocumentLock`** (Core/Utilities.js:80) — `LockService.getDocumentLock()`, `waitLock(30000ms)`, always releases in `finally`. Every write-triggering entry point already uses this. The sync engine's controller and every task handler will wrap in this exact call — no new locking primitive needed.

**3. Only one existing time-driven trigger: `PayTrackerCalendarAutomationService`** (Calendar/CalendarAutomationService.js) — `getStatus()/enable()/disable()`, status always *derived live* from `ScriptApp.getProjectTriggers()` (never cached in PropertiesService), `enable()` guards against duplicate triggers, `disable()` removes all matching triggers. The handler is a bare top-level function (`runAutomaticPayTrackerCalendarSync`) that immediately wraps in `withDocumentLock`. This exact shape is the template for every new trigger the engine installs — confirmed as the only precedent, so there's no competing convention to reconcile.

**4. Zero `CacheService` usage anywhere.** If the engine needs short-lived cross-request state (e.g. "a sync is currently in progress, don't show stale 'Waiting'"), there's no existing convention — `PropertiesService` (already used for Monzo tokens) or the new Sync Status sheet itself are the only established persistence mechanisms.

**5. Monzo's OAuth refresh has no headless path.** `refreshAccessToken()` throws `'Your Monzo connection has expired. Reconnect Monzo from Finance to continue syncing.'` if the refresh token is invalid/expired — this requires an interactive browser redirect through Monzo's consent screen. A scheduled trigger firing overnight **will** hard-fail once this happens; there is no way to make it headless. Design implication: Monzo must be a **non-critical** task — its failure must degrade to "last known good" display, never block startup or other tasks, and the failure message must be actionable ("Reconnect Monzo from Finance") rather than a generic error. This is exactly the kind of failure the spec's stop-condition #1 describes if it happens for real during this session — but designing *for* its possibility is in-scope and required.

**6. The existing "global refresh" button doesn't actually refresh everything.** `#refresh-app-button` → `refreshApplication()` (App/AppController.html:952) only re-fetches the bootstrap and force-reloads the Dashboard — it does not reload Action Centre, Pay, Finance, Savings, Calendar, etc. "Refresh Everything" (Phase 4/PR C) needs to become a real Unified-Sync-Engine-backed action, not just relabel the existing partial one.

**7. Dashboard is the one workspace that doesn't gate its first load on the route-change event** — it loads unconditionally on `DOMContentLoaded` regardless of the actual starting route (App/AppController.html vs DashboardService.html:1642). Every other workspace service (Action Centre, Pay, Finance, Savings, Calendar, Reports, Payroll Centre, Annual Leave, Staffline, Settings, Goals, Pay Adjustments, Transaction Rules) is confirmed still gated on `paytracker:routechange` matching its own route — **PR #26's fix is fully intact**. The new startup sync sits *before* this existing flow (in the loading screen), so this quirk doesn't block Phase 1-6, but it's relevant to Phase 5's page-integration work.

**8. Gmail-imported payslips are never auto-processed today** — `scanGmail` only registers metadata + saves the PDF; nothing calls `processPayslip`/`processBatch` afterward except a manual upload's own inline call, or unreachable test functions. If Phase 2 wires payslip auto-processing into the sync engine, this is net-new automated behaviour, not a re-wire of something already safe in production — extra caution and explicit dry-run-style verification is warranted before enabling it unattended.

**9. `AUTO_CONFIRM_THRESHOLD: 95`** (FinanceIntegrationConfig.js:330) is declared but referenced nowhere — dead config, not a live gate. Not a blocker, but flagged so it isn't mistaken for an existing auto-confirm mechanism when it doesn't do anything.

## Recommended freshness TTLs (input to Phase 3, not final)

| Task | Suggested TTL | Rationale |
|---|---|---|
| Calendar | 15 min | Already has a 6h trigger; shifts change infrequently intraday |
| Staffline Gmail | 6h | Timesheet approvals arrive on Staffline's own schedule, not continuously |
| Payslips | 6h | Payslips arrive weekly/monthly; no benefit to frequent checks |
| Annual Leave Gmail | 6h | Same reasoning as Staffline |
| Monzo transactions | 15 min | Existing 30-day rolling window already assumes frequent, cheap re-sync |
| Monzo pots | 15 min | Balance changes are meaningful to see promptly |
| Reconciliation | 0 (always recompute) | Confirmed zero writes, cheap, pure function of already-fresh sources |
