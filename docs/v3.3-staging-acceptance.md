# v3.3 Staging Acceptance

**Release candidate:** `release/v3.3.0-rc1` = PRs #47 → #48 → #49 → #50 → #51 in a straight line on top of `main` `64cf359` (fast-forward; no merge conflicts possible).
**Rule:** nothing here touches production until step 9, and step 9 needs your explicit go-ahead. Pay Tracker never moves money.

## A. Isolation: checked in the code, not assumed

| Risk | What the code actually does | Result |
|---|---|---|
| Staging writes to the production spreadsheet | Every sheet read and write uses `SpreadsheetApp.getActiveSpreadsheet()`; there is no `SpreadsheetApp.openById` anywhere | A staging **copy** can only change itself |
| Pushing staging code over production | `tools/staging-push.cjs` pushes from a temporary folder with its own `.clasp.json`, **refuses the production Script ID**, and never edits the repo's `.clasp.json`. Its file list is identical to clasp's own (183 files, checked) | Wrong-project push blocked |
| Production Monzo tokens | Client ID/secret are in *script properties* and tokens in *user properties* of the script project; **neither is copied** with a spreadsheet copy | Monzo is inert in staging unless you add credentials there |
| Duplicate bank transactions | Staging only reads the Bank Transactions copied with the spreadsheet; import de-duplicates by Monzo transaction ID (tested) | No duplicates; the self-check verifies it |
| Gmail | No label, read-state or send calls; Gmail scope is read-only | Staging imports can't change your mailbox |
| Drive | Payslip import saves PDFs under a folder ID held in a *script property* (not copied) | Staging creates its **own** folder in your Drive (harmless, but expect it) |
| Scheduled syncs | Triggers are not copied | Don't enable automatic sync in staging |
| Manual corrections | v3.3 never overwrites a row that differs from what Calendar last wrote | Preserved; `previewCalendarManualOverrides()` lists them first |

**Monzo in staging: don't connect it.** Connecting would need your Monzo client credentials in the staging project and a second authorisation of the same Monzo account. Whether Monzo then ends the production session is not established, so the safe default is to test matching on the copied Bank Transactions (plus the offline Monzo tests).

## B. Set up staging (needs your Google account)
1. Production editor → **Deploy → Manage deployments**: note the production deployment ID and version (expected **@143**; it couldn't be checked from development). Spreadsheet → **File → Version history → Name current version** "Before v3.3".
2. Spreadsheet → **File → Make a copy**, named **"Pay Tracker STAGING v3.3"**. "STAGING" must be in the name: the self-check refuses anything else.
3. Staging copy → Extensions → Apps Script → Project Settings → copy the **Script ID**.
4. On the development machine (dry run first; it lists the target and every file):
   ```bash
   node tools/staging-push.cjs <STAGING_SCRIPT_ID>
   node tools/staging-push.cjs <STAGING_SCRIPT_ID> --push
   ```
5. Staging editor → **Deploy → New deployment → Web app** (Execute as: Me; Access: Only myself).
6. Staging editor → run `previewCalendarManualOverrides()` (read-only). Check that each listed row really is one you corrected by hand.
7. Staging web app → **Refresh** once (the first v3.3 sync, on the copy).
8. Staging editor → run **`runPayTrackerAcceptanceChecks()`** (read-only). It checks:

   | Area | Automated check |
   |---|---|
   | Environment | It's the STAGING copy; no triggers; Monzo not connected |
   | Calendar | Every calendar readable; all 24 NHS combinations (4 shifts × 2 hospitals × weekday/Sat/Sun); rows to be kept as manual |
   | Payroll | £90.95 (w/e 04/10), £166.96 (w/e 11/10), ×1.33 £71.68, NHS £95.33 and £105.75; **7 Oct and 15 Oct** NHS rows = Basic £95.33 |

   Every **FAIL** must be fixed; every **REVIEW** must be explained. Send me the log if anything is unclear.
