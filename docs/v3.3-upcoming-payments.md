# Step 2B — Dynamic Upcoming Payments (issue #46)

Status: implemented on `feature/upcoming-payments` (draft PR, stacked on Step 2A). **Not deployed.**

## What the user sees

| Where | What |
|---|---|
| Dashboard (top) and Finance → Overview | The next **five** Bills and Subscriptions in date order, with totals due in the next 7 and 30 days. A card opens the matching Bills/Subscriptions tab. |
| Finance → Bills | Bills only: full 30-day timeline (recurrences projected), then *Payment history*. |
| Finance → Subscriptions | Subscriptions only: same card and timeline, then *Payment history*. |

Each card: initials icon (no merchant logos are stored, so this is the fallback for every merchant), name, kind · frequency, amount (or "Amount varies"), status label, countdown ("In 5 days", "Due today", "3 days ago"), due date, the evidence behind its status, and a price-change note. Status is always written as text, not only shown by colour. A freshness line shows when the data was built, when Monzo last synced, and a warning if Monzo is not syncing. *Check Monzo now* runs only the `MONZO_TRANSACTIONS` sync task, then refreshes the cards.

## Canonical model

`Backend/Finance/PaymentTimeline.js` (pure) works in two stages:

1. **`buildSeries(sources)`**: one *series* per active bill and per confirmed, active subscription, with the next unresolved due date and the evidence for it. It is plain JSON that doesn't depend on today's date, so it can be cached.
2. **`present(model, today)`**: works out each status and countdown for *today*, projects recurrences inside 30 days, sorts, totals, and builds history.

Sources (all existing sheets, read once each, never written): Bills, Finance Payments, Payment History, Subscriptions, Subscription Transactions, Bank Transactions, Sync Status. No schema change.

### Statuses
| Status | Rule |
|---|---|
| Upcoming | due after today |
| Due today | due today |
| Awaiting confirmation | 1–3 days past due, no evidence (bank payments post late) |
| Overdue | more than 3 days past due, no evidence |
| Needs review | a *Suggested* (unconfirmed) bank match or subscription link, or a Finance Payments processing *Error* |
| Paid | moves to history; the next occurrence appears in Upcoming |

**Never paid by date alone.** Paid needs: a *Confirmed/Automatic* bank match to the Finance Payments row (the existing `TransactionMatchingService`), the row's *Paid?* tick, or a confirmed Subscription Transactions link dated 5 days before to 10 days after the due date. A *Rejected* match is ignored. Nothing is deleted.

### No double counting
- A subscription with `Linked Bill ID` pointing to an active bill, or with the same name and amount (±1%) as one, is shown **once, as the bill**. A note says so.
- One bank transaction confirms at most one payment, and appears in history once.
- Debt repayments are not Bills or Subscriptions and are not shown.
- Unreviewed (*Needs Review*), rejected, cancelled and paused subscriptions are not shown. A note counts the unreviewed ones.

### Dates
- Calendar days in the script time zone (Europe/London). Day differences use `Date.UTC`, so the clock changes are safe.
- Monthly, quarterly and annual steps keep the anchor day and clamp to short months: 31 Jan → 28 Feb → 31 Mar; 29 Feb → 28 Feb next year.
- "Next 7 days" means today plus the following 6 days. "Next 30 days" works the same way.
- **Fixed in passing:** `PayTrackerPaymentService.advanceDateByFrequency` used `setMonth(+1)`, so a bill due 31 Jan advanced to **3 Mar** and February's payment was skipped. It now clamps. A bill's stored next due date can still drift to the 28th after a short month, because only one date is stored; the timeline itself never drifts.

## Performance

**What makes the app feel slow (from the code; the live Sync Status `Duration Ms` could not be read from this machine):**

1. **Startup waited for every source to sync.** `initialize()` awaited the whole Unified Sync pass (Calendar, three Gmail imports incl. payslip PDFs, Monzo, pots, reconciliation) in one server call before hiding the loading screen. A *Continue* button only appeared after 7s and had to be clicked. **Change:** after 4s the existing "continue in background" path runs automatically; the pass keeps going; a new `paytracker:syncfinished` event reloads the Dashboard and Upcoming Payments when it ends. A pass that finishes within 4s behaves exactly as before.
2. **Finance page** (`getPayTrackerFinanceWorkspace`) re-syncs the payment queue and recalculates the Finance Dashboard sheet on every load. That's unchanged, but Upcoming Payments no longer depends on it: the cards use their own read-only endpoint.
3. **Monzo import wrote one row per call** (`appendRow` per transaction). **Change:** one batched `setValues` for all new transactions, with the row layout unchanged.

**Upcoming Payments endpoint:** `getPayTrackerUpcomingPayments({refresh})`.
- A cached answer (CacheService, 6h) reads **no sheet**. A rebuild reads 7 sheets, once each.
- It never syncs, never calls Monzo, never takes a lock, never writes.
- The browser shows cached data first, then asks for a rebuild in the background.
- The cache is cleared after any Finance workspace call and after a Monzo transaction sync. Statuses are always recomputed for the current day, so cached data is never wrong about *which day it is*, only about bank data newer than `builtAt` (which is shown).

### Data fix
A Monzo transaction first imported while **pending** was never updated: Monzo returns it again once settled, but `storeTransactions` skipped every known ID. So the row stayed *Pending* with no settled date for ever, and Step 2A's cash-flow preview never counted it. Settled transactions now update Settled At, Amount, Direction, Pending and Declined on the existing row only. Match and category columns are never touched.

## Monzo webhooks: not feasible on the current hosting (not implemented)
- The web app is deployed `access: MYSELF`, `executeAs: USER_DEPLOYING`. Monzo's servers can't authenticate as you, so they can't reach a `doPost`. None exists.
- Making the deployment `ANYONE_ANONYMOUS` would expose the **whole** web app (`doGet`, which runs as you and returns your financial data) to anyone with the URL. That's not acceptable.
- Apps Script web apps answer POSTs with a 302 redirect, which webhook senders commonly treat as a failed delivery.
- Monzo webhook payloads aren't signed. Authenticating one would rest on a secret in the URL, so it would need replay protection by transaction ID.

**If near-real-time ever matters:** a separate, minimal Apps Script project (or Cloud Function) deployed anonymously, whose `doPost` only checks a long random path secret, then queues `{transaction id, received at}` into a dedicated sheet or Properties. Its idempotency key is the Monzo transaction ID. The main app's scheduled sync would then drain the queue and fetch that transaction through the existing authenticated API. This needs new deployment and credential decisions from the owner. Until then: the 15-minute `MONZO_TRANSACTIONS` freshness, the scheduled pass, and *Check Monzo now*.
